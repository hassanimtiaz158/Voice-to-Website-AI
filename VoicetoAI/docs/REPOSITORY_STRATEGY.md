## 1. Branching Model: Trunk-Based Development

To maintain high development velocity and prevent complex merge conflicts across the four vertical slices, the platform adopts a strict **Trunk-Based Development** model with short-lived feature branches.

```
      (Feature Branch: feat/clarifier-interrupt)
         o───o───o
        /         \  (Pull Request + Ring Review + CI Green)
───────o───────────o─────────────────────────────────────────► main (Production Ready)
        \         /
         o───o───o
      (Feature Branch: feat/sandbox-precache)
```

### 1.1 Branch Naming Conventions
All branch names must be prefixed with their operational intent:
- `feat/<slice-name>-<short-description>`: New functional capabilities (e.g., `feat/member1-whisper-vad`).
- `fix/<issue-description>`: Bug repairs and test failure remedies (e.g., `fix/sandbox-vite-memory`).
- `spike/<investigation-name>`: Time-boxed research probes (e.g., `spike/github-mcp-rate-limit`).
- `eval/<benchmark-name>`: Benchmark harness updates (e.g., `eval/bilingual-wer-dataset`).
- `chore/<tooling-change>`: Dependency updates, CI workflows, or pre-commit scripts.

### 1.2 Main Branch Protection Rules
The `main` branch represents deployable production state. Direct pushes to `main` are cryptographically and administratively blocked:
1. **Require Pull Request Reviews:** Minimum 1 approving review from the designated ring reviewer.
2. **Require Status Checks to Pass:** GitHub Actions CI must pass:
   - Python linting (Black, Flake8) and MyPy type checks.
   - Frontend linting (ESLint, Prettier) and TypeScript compilation (`tsc --noEmit`).
   - Pydantic contract test suite (`pytest contracts/`).
   - Core backend unit and integration tests.
3. **Linear History:** Merge commits are disabled in favor of **Squash and Merge**, ensuring clean, atomic commit logs on `main`.

## 2. Peer Review Protocol: The Ring Review Rule

To ensure cross-functional system understanding and eliminate single-points-of-failure in knowledge distribution, all pull requests must be reviewed by the next team member in the clockwise ring:

```
               ┌────────────────────────┐
               │ Member 1: Conversation │
               └───────────┬────────────┘
                           │ Reviews PRs from Member 4
                           ▼
┌────────────────────────┐   ┌────────────────────────┐
│ Member 4: Delivery     │   │ Member 2: Generation   │
└───────────▲────────────┘   └────────────┬───────────┘
            │                             │
            │ Reviews PRs from Member 3   │ Reviews PRs from Member 1
            │                             ▼
            │                ┌────────────────────────┐
            └────────────────┤ Member 3: Edit & RAG   │
                             └────────────────────────┘
```

### Review Invariants:
- A reviewer must execute the PR's test suite locally or inspect CI logs before signing off.
- Any change affecting the `contracts/` directory requires approval from **all three other team members**.

## 3. Commit Message Standards: Conventional Commits

All commit messages must adhere to the Conventional Commits specification:
```text
<type>(<scope>): <short description>

[optional body]

[optional footer(s)]
```

### Allowed Types:
- `feat`: A new feature for the user or platform.
- `fix`: A bug repair.
- `docs`: Documentation changes only.
- `refactor`: Code change that neither fixes a bug nor adds a feature.
- `perf`: A code change that improves performance or latency.
- `test`: Adding missing tests or correcting existing tests.
- `ci`: Changes to CI/CD configuration files and scripts.

## 4. Git Tagging Strategy

### 4.1 Platform System Tags
Platform releases follow Semantic Versioning (`vMAJOR.MINOR.PATCH`):
- `v0.1.0-m0`: End of Milestone M0 (De-risking Spikes).
- `v0.2.0-m1`: End of Milestone M1 (Core Engine).
- `v0.3.0-m2`: End of Milestone M2 (Create Flow).
- `v0.4.0-m3`: End of Milestone M3 (Edit & Versions).
- `v0.5.0-m4`: End of Milestone M4 (Marketplace & Money).
- `v1.0.0-final-fyp`: Final production release submitted to academic committee.

### 4.2 Generated Project Repository Tags
Every project generated by the platform is backed by its own private GitHub repository. Versioning within generated user repositories follows strict build verification tags:
- `v1`: Initial greenfield build verified by Sandbox and Playwright.
- `v2` ... `vN`: Incremental surgical edits verified and committed to `main`.
- `draft/failed-vN`: Quarantined build attempts that failed verification after 3 Fixer retries (never merged to `main`).

## 5. GitHub MCP & Repository Provisioning Architecture

The backend interacts with GitHub via the official GitHub Model Context Protocol (MCP) server running as a dedicated subprocess or microservice.

```
┌────────────────────────┐     JSON-RPC / stdio    ┌───────────────────────┐
│ FastAPI Committer Node │ ──────────────────────► │ GitHub MCP Server     │
│ (backend/app/mcp)      │                         │ (github-mcp-server)   │
└────────────────────────┘                         └───────────┬───────────┘
                                                               │
                                                               ▼ HTTPS REST / GraphQL
                                                   ┌───────────────────────┐
                                                   │ GitHub Organization   │
                                                   │ (voicetoai-projects)  │
                                                   │  ├── proj-1234 (v1)   │
                                                   │  ├── proj-5678 (v2)   │
                                                   │  └── ...              │
                                                   └───────────────────────┘
```

### 5.1 Repository Naming & Ownership
All client repositories are created under a centralized GitHub Organization managed by the platform:
- Repo Pattern: `voicetoai-projects/site-{project_id_prefix}-{slug}`
- Visibility: `private`
- Default Branch: `main`

### 5.2 Scoped Developer Access Tokens
When a freelance developer is assigned to deploy a project, the platform generates a temporary **GitHub App Installation Access Token**:
- **Scope:** Read-only access to repository contents (`contents: read`).
- **TTL:** 4 hours.
- **Revocation:** Automatically invalidated upon ticket completion or cancellation.
